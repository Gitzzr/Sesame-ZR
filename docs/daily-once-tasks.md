# 「一天一次」任务：机制、清单与核对台账

> 配套：[`architecture.md`](architecture.md)（离线/暂停状态机见 §11）、[`user-guide.md`](user-guide.md)（界面上的入口）、[`../TODO.md`](../TODO.md)
>
> 本文是**唯一维护入口**：新增/调整「每日一次」限制都在这里登记。

## 1. 为什么需要它

蚂蚁系的多数任务**服务端一天只认一次**，但模块是按轮次反复跑的（默认约 50 分钟一轮）。
不做限制时，同一个任务当天会被重复处理几十次：

| 任务 | 2026-09-28 当天次数 |
| --- | --- |
| 庄园任务[秋叶月饼任务] / [完成 N 笔旧衣回收] / [逛闪购外卖 N 元起吃] | 各 44 |
| 庄园任务[到店付款] | 40 |
| 绿色打卡🍀[各项] | 46 |

代价是**白跑请求**（在风控窗口里放大请求量）与**日志被淹没**。

但「限制」本身有反作用：一旦把某个**没成功**的任务误判成"今天已完成"，它就会整天不再执行，
而且事后无从发现。所以本文描述的不只是限制，还包括**核对机制**。

## 2. 现有机制（不要另造轮子）

| 机制 | 粒度 | 说明 |
| --- | --- | --- |
| `Status.hasFlagToday` / `setFlagToday` | 任务级 | 标志存在 `status.json` 的 `flagList`，**跨日整体清空** |
| `farm::task::limit::$bizKey` | 任务级 | 庄园任务：**服务端返回 `309 已达上限` 或本地判定成功**后置位，当天不再处理 |
| `EcoLife::tick::$actionId` | 任务级 | 绿色打卡：逐项锁定，已成功的不再重复提交 |
| `CustomSettings.onlyOnceDailyList` | 模块级 | 「选中每日只运行一次的模块」，**默认关闭**；默认名单 7 个：`antOrchard` / `antCooperate` / `antSports` / `antMember` / `EcoProtection` / `greenFinance` / `reserve` |

**铁律：只在服务端返回成功时锁定。** 失败、未受理、状态未推进一律不锁，当天继续尝试。

## 3. 核对机制（防止「限制了却没完成」）

因为 `flagList` 跨日清空，第二天看不出「昨天限制过什么、有没有完成」，所以额外做了一层台账：

| 层 | 位置 | 用途 |
| --- | --- | --- |
| 台账文件 | `config/<userId>/daily_once.json` | 记录每次**首次成功**（`flag` / 名字 / 时间），保留 **7 天**、跨日不清 |
| 代码 | `task/DailyOnceAudit.kt`（纯逻辑部分可单测） | 写入与读取台账，`merge` / `trim` / `dayKey` 均为纯函数 |
| 界面 | 日志中心 → 今日完成 → **「每日一次」区块** | 列出当天已锁定的项与首次成功时间 |
| 日志 | `record.log` 的 `📌 每日一次已锁定：… \| flag=… \| day=…` | 可按天 grep 回溯 |

**第二天怎么核对**：打开「今日完成」，看「每日一次」区块里有哪些项。

- 出现了 ⇒ 该任务当天**确实成功过**一次，限制是安全的；
- 本该有却没出现 ⇒ 它当天**根本没成功**，需要检查是不是被误锁（或服务端本身没给）。

台账保留 7 天，也可以直接看文件：

```bash
adb shell cat /sdcard/Android/media/com.eg.android.AlipayGphone/sesame-TK/config/<userId>/daily_once.json
```

### 4.3 第三批已落地：AI摸鱼被拒收的任务当天不再重试（2026-09-30，PR #41）

**C1 的最终口径**（两轮真机抓包后确定）：重复的确实是**未受理**，而且原因不是参数写错 ——
是**这类任务在客户端根本没有完成通道**。抓包证据：

1. **主进程**（`debugMode` 抓包，见 `.workbuddy/debug-logs/capture/`）：用户手动完成
   「玩任意一款游戏30s」并领奖的全流程里，**没有任何 `finishTask` 调用** ——
   只有 `listTask`（poll）与 `receiveTaskAward`（领奖）。任务状态是**服务端自己变成 FINISHED** 的。
2. **小游戏所在沙箱进程**：小游戏跑在 `:liteN` 进程（模块原先只注入主进程）。
   给沙箱进程装上抓包钩子（`HookUtil` 日志确认安装成功）后，在游戏里玩满一分钟，
   **依然 0 条 RPC** —— 完成证据由游戏侧/服务端校验产生（`taskCategorization` 为 `Commercialization`，
   本质是买量转化任务），客户端没有可复刻的接口。

因此落地口径**只保留有证据支撑的部分**：

| 情形 | 处理 |
| --- | --- |
| 任务完成 | 照常，状态转 FINISHED 后领奖 |
| `finishTask` 被服务端拒收 | **登记放弃，当天不再重试**（`antOcean::aiFish::abandon::<taskType>`）+ 台账留痕 |

⚠️ **刻意不按 `taskProdPlayType=OTHER` 预判"需手动"**：实测同为 `OTHER` 的
「去阿宝测一测我的摸鱼运势」「添加海洋至支付宝首页」都能被 `finishTask` 正常完成并领奖
（2026-09-30 01:54 日志：`AI摸鱼任务完成已确认` + `AI摸鱼奖励领取已确认`）。
按类型预判会把这些**能做的任务一起跳过** —— 所以改为"试一次、被拒就记下来"：
一次请求换一个确定结论，比猜可靠。

⚠️ **也刻意不做"答题链"分支**（曾经写过一版，已删）：曾设想对跳转链接里带
`activityId` 的任务复用 `ReadingDada` 的 dada 答题链，但两台设备实测该任务的
`taskJumpUrl` 都**不含 `activityId`**（K50 2026-09-30 03:26 日志走的是
`AI摸鱼任务等待0秒 → 完成未受理`，即 `finishTask` 路径），分支从未命中过 ——
**没有证据支撑的分支不留**。

- 放弃与完成是**两套标志**：只拦「替用户完成」，**不拦 FINISHED 状态的领奖分支** ——
  用户在宿主应用里手动做完之后，模块下一轮照常领奖；
- 留痕：`DailyOnceAudit` 写 `海洋AI摸鱼[未受理不再试][任务名]`，
  次日「今日完成」页能看到它为什么没做成；
- 后续轮次**静默跳过**（不逐轮报「跳过」，避免给 ocean.log 添几十行/天噪音）；
- **实测收益**：09-29 全天 85 次无效调用；09-30 小米17 上旧版在 00:02/00:24/00:38
  三个时刻反复重试共 10 次，新版每任务每天最多 1 次 —— 03:11 试一次被拒后，
  03:15 的整轮海洋任务（14 秒）**0 次重试**。

**已知边界**：被拒收的是游戏中心渠道任务/买量转化类（如「玩任意一款游戏30s」「玩一玩X」
「去森林市集答题」），要真人去做 —— 这是任务本身的设计（完成证据由游戏侧/服务端校验）。
抓包实证：主进程全流程无 `finishTask` 调用；小游戏所在 `:liteN` 沙箱进程装上抓包钩子后
玩满一分钟同样 0 条 RPC。模块负责"把浪费降到 1 次 + 说明原因 + 事后自动领奖"，不做 UI 代玩。

## 4.4 「无进展即退出」：比"一天一次"更基本的一条（2026-09-30，PR #42）

C1 之外还有一类噪音：**服务端一直回成功、但任务状态不推进**，而循环的继续条件只看
「有没有 RPC 返回成功」——于是空转数小时。2026-09-30 小米17 实测到三处：

| 位置 | 现象 | 处理 |
| --- | --- | --- |
| 庄园抽抽乐 `ChouChouLe.doChouchoule()` | 同任务「游戏充值得10次机会」**1 次/秒空转 8.4 小时**（19,120 行日志、≥3.8 万次 RPC），期间只抽到 1 次奖 | 每轮对「任务状态 + 剩余次数」做快照，整轮无变化即退出（`ChouChouLeLoopPolicy`），另加 5 轮上限兜底 |
| 会员商家服务 `AntMember.doMerchantMoreTask()` | 递归自调用 + `doubleCheck` 无条件置位 → **约 2 次/秒重试 905 次**（单分钟峰值 78） | 改为有轮次上限（3）的循环，只有服务端受理才算推进；报错当轮即停 |
| 森林活力值兑换 `Vitality.handleVitalityExchange()` | `MONEY_NOT_ENOUGH`（活力值不足）**345 次/天**，每个轮次都撞 | 当天最多尝试 2 次（余额当天会涨，全禁会错过），超限静默跳过 |

**通用原则**：循环/递归的退出条件必须是「**状态推进**」，不能是「**调用返回成功**」；
判定抽成 `*Policy` 并配契约测试（本项目硬规则 5）。

## 6. 新增一项「每日一次」的步骤

1. 确认该任务**服务端确实一天一次**（看日志里是否出现 `309 已达上限`、`剩余次数`、`已完成` 等信号）；
2. 在任务的**成功分支**里，先 `Status.setFlagToday("<前缀>::<标识>")`，再
   `DailyOnceAudit.record(UserMap.currentUid, flag, "可读的名字")`；
3. 在任务的**入口**加 `if (Status.hasFlagToday(flag)) return/continue`；
4. 命名约定：`<模块或功能>::<语义>::<对象 id>`，例如 `farm::task::limit::SHANGOU_xiadan`、
   `EcoLife::tick::photoguangpan`；
5. 补单测（纯逻辑部分）并更新本文的 §4 / §5；
6. 第二天按 §3 核对一遍，确认「锁定的都真完成了」。
