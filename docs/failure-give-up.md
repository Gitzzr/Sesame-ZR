# 重复失败放弃（当天失败到上限就停止尝试）

面向**维护者与使用者**的机制说明与**限制清单**。
最近更新：**2026-10-01**（首次落地，含首轮代码审查后的修订）。

相关代码：`model/RepeatFailurePolicy.kt`（判定，纯逻辑）、`task/RepeatFailureGuard.kt`（接线与播报）、
`data/Status.kt` 的 `failureCountTodayList`（当天计数）。契约测试：`RepeatFailurePolicyTest`。

---

## 1. 这份机制解决什么

真机日志显示，有一批调用**每轮都失败、当天从未成功**——主任务一天跑几十轮，它们就失败几十次：

| 目标 | 当天失败 | 服务端回应（原文） |
| --- | --- | --- |
| 信用2101 账户查询 | 39 | 返回为空或非 SUCCESS（**注意：实际回应常是空响应占位，见 §3 L2**） |
| 运动竞猜 participate | 39 | `{"error":3000,"errorMessage":"系统出错，正在排查"}` |
| 会员宝箱 | 39 | `resultCode=PARAM_ILLEGAL` / `resultDesc=系统繁忙，请稍后重试` |
| 芝麻炼金 joinActivity | 32 | `生活记录模板不存在` |
| 学生签到 queryCheckInModel | 25 | Check failed |

**量化（红米 K50，2026-09-30）**：当日 `error.log` 共 479 条，**89%（428 条）来自 18 个重复模板**。
这些目标是其中约 210 条/天。按上限 5 次收敛后理论降到约 25 条/天 ——
**这是上界估计**：实际降幅取决于其中有多少次属于 §3 L2 的"不计入"情形
（那部分不会触发放弃，因此仍是"每轮一条"）。

## 2. 机制

```
调用前： if (RepeatFailureGuard.shouldSkipToday(KEY)) return      // 今天已放弃 → 静默跳过
调用后失败： RepeatFailureGuard.recordFailure(KEY, "给用户看的名字", 回应文本…)
```

- **计数**：`Status.failureCountTodayList`（`<key> → 当天失败次数`），落盘在
  `config/<uid>/status.json`；**跨天随 `Status.unload()` 清零**（与其他每日字段同一套机制）。
- **阈值**：`RepeatFailurePolicy.DAILY_FAILURE_LIMIT = 5`。达到 5 次后该 key 当天不再被调用。
- **硬豁免**：`RPC_VERIFICATION_REQUIRED`（安全验证）与 `EMPTY_RPC_RESPONSE`（空响应占位）
  **一律不计入**（见 §3 L2）—— 它们不是业务失败。
- **播报**：只在**恰好达到上限那一次**写一行 `Log.record`，并写一条每日台账。
- **跳过要静默**：由调用方在"调用前"判断，因此不会走到失败分支。
  （注意口径：**错误日志**静默；像信用2101 那样在入口拦的，`debug.log` 里仍会每轮留一行跳过说明。）
  实现时特别注意过：像信用2101 那种"查询失败即整个流程静默"的任务，
  必须在**流程入口**拦住，否则失败分支仍会每轮写一条 error（见 §5 的副作用列）。

### 2.1 台账的副作用（别忽略）

放弃时调用的 `DailyOnceAudit.record(uid, "fail::<key>", …)` 与「一天一次锁定」**共用同一个台账文件**，
所以：

- 宿主日志里会多出一行 `📌 每日一次已锁定：失败放弃：…`（措辞与"任务已锁定"混淆）；
- 「今日完成」页会把它当成一条"已锁定/已处理"的记录展示（目前**没有**按 `fail::` 前缀分区）。

这是已知的表述瑕疵（见 §3 L8）。要精确区分需再改台账页面，暂列为待办。

## 3. ⚠️ 限制清单（使用/评估本机制前必读）

### L1 阈值对两类失败是**同一个值**：不可用类也是"当天放弃"，不是退避

机制把失败归类为 `DETERMINISTIC`（确定性）与 `TRANSIENT`（服务端不可用），
但**两者都在 5 次后停止尝试**——类别目前**只影响日志/台账措辞**，不影响阈值。

- **代价**：若某接口只是当天某个时段故障（例如维护两小时），5 次失败多半发生在故障期，
  之后即使服务恢复也不再尝试，**该目标的当天收益就丢了**。
- **为什么不区分阈值**：客户端**无法可靠区分**"临时故障"与"长期不可用"。
  实测反例：运动竞猜的 `error 3000 系统出错` 像是临时故障，实际全天 39/39 全失败。
  分开阈值只会制造"更聪明"的假象，把误判风险换成少拿收益。

### L2 **安全验证与空响应不计入**（硬性，不得放开）

`RPC_VERIFICATION_REQUIRED`、`EMPTY_RPC_RESPONSE`（以及 `触发安全验证` 文案）**不计数**。

理由：安全验证是**暂停**（有 TTL、会自愈），离线是"自愈后应重试"；
若把它们算进预算，几轮之后就会写出"该功能今天不再尝试"——
项目硬规则 3 明确把"该功能今天不再尝试"列为禁忌。
判据与 `hook/RequestManager.kt`、`hook/VerificationPausePolicy.kt` 的常量与文案对齐：
**宿主会把原始风控响应直接回给调用方**（不走占位替换），所以只认错误码会漏判，
豁免清单里同时列了 4 条风控文案；`RepeatFailurePolicyTest` 有一条**交叉断言**
（`VerificationPausePolicy.VERIFICATION_TEXTS ⊆ NON_COUNTED_HINTS`）防止两处漂移。

**副作用**：若某目标的失败**主要来自空响应**（例如信用2101 的"返回为空"），
它就不会触发放弃，仍会每轮产生一条日志 —— 这是刻意的取舍（宁可不降噪，也不误放弃）。

### L3 计数是**当天累计**，不是"连续失败"

白天失败 4 次、晚上再失败 1 次，同样会触发放弃。
某目标若天然只在特定时段可做、其它时段必失败，不要接入本机制。

### L4 类别判定是**关键词匹配**，不理解业务语义

`RepeatFailurePolicy.kindOf(...)` 用小写化子串表匹配；服务端改文案会退化成 `UNKNOWN`，
`UNKNOWN` 的处理是**继续尝试**（宁可多试，不误放弃）。这是刻意的安全方向。
新增判据必须同时更新 §4 表与 `RepeatFailurePolicyTest`（后者会遍历整表）。

### L5 key 由调用方手工指定；**两个不同目标共用 key 会互相消耗预算**

计数按 key 存。重命名 key（或改了拼进 key 的变量）会让当天计数重新从 0 开始 ——
不会造成错误，只是多试几次。反之，**两个逻辑目标误用同一个 key 会提前放弃**，
所以带循环性质的 key 必须带上区分字段（例：会员宝箱的 key 是
`member::treasureBox::<bizNo>`，因为一天可能有多个宝箱）。

⚠️ **反向风险**：带进去的字段若**每轮都变**（例如服务端每次重新生成 `bizNo`），
key 就永远攒不到 5 次 —— 机制会**静默失效**（表现为"该目标仍每轮失败"）。
`bizNo` 目前看是服务端下发的稳定业务号，但**尚未在真机核对**（见 L12）；
若发现 `failureCountTodayList` 里同一功能出现多个 `member::treasureBox::*` 条目，
应改回不带变量、或改用更稳定的字段。

### L6 只适合"一天最多成功一次"的目标

本机制不理解"成功了几次、还该成功几次"。**一天本该成功多次**的目标（浇水、帮喂、收能量等）
接入会直接少拿收益 —— 这类要靠名单次数上限（见 `interaction-limits.md`）。

### L7 不覆盖的失败类型（各有归属，别硬塞进来）

| 失败类型 | 归属机制 | 本机制的处理 |
| --- | --- | --- |
| 代码异常 / 崩溃 | `ExceptionMode.PROTECTIVE` 统一异常出口 | 不涉及（guard 只接在"服务端回应"分支） |
| RPC 层连续失败（网络/超时） | RPC 有界熔断（`NewRpcBridge.maxErrorCount`） | 通常落到 `EMPTY_RPC_RESPONSE` → **不计入**（L2） |
| 安全验证 / 服务端繁忙 | `VerificationPausePolicy`、`ServerBusyPolicy` | 安全验证 → **不计入**；繁忙类按 §4 归类 |
| 需要真实交互/无客户端通道的任务 | `daily-once-tasks.md` §4.3（AI 摸鱼按天放弃 + 台账） | 不重复实现 |
| 达上限类（`QUOTA_*`、`已达上限`） | 各任务的当天标志（如 `forest::VitalityExchangeLimit::*`） | 不重复实现 |
| 单次执行内的循环 | 无进展退出（`ChouChouLeLoopPolicy`、商家任务轮次上限） | 不重复实现 |

### L8 已知的表述瑕疵：台账复用

见 §2.1：放弃记录会以「📌 每日一次已锁定」的措辞出现在日志与「今日完成」页里。
信息没错（确实记了一条），但与"任务锁定"的语义混在一起。

### L9 播报"只发一次"依赖计数落盘

`recordFailure` 在**恰好等于上限**时播报。若那一轮进程被杀、`status.json` 未落盘，
下次可能再次触发播报（多一条日志），概率极低且无副作用。

### L10 跨天后的**第一次失败**可能被吞掉

`markFailureToday` 先自增再 `save()`；若这次 `save()` 恰好跨天，内部
`updateDay → unload()` 会把刚自增的计数连同当天状态一起清掉 —— 表现为跨天后首次失败没被记住
（后果只是"多试一次"，不会造成错误）。

### L11 上限 5 的取值依据只有单日样本

5 次 ≈ 39 轮/天的前 13%，足以把噪音压到可接受，同时保留"换个时段说不定能成"的机会。
样本只有一两天的日志，**不是统计结论**；调整时请同步 §4 表、`RepeatFailurePolicyTest`
（含 `DAILY_FAILURE_LIMIT` 的断言）与本文档。

### L12 **未做真机验证**（截至 2026-10-01）

落地时只做了编译与契约测试，以下各项**必须**用之后的真机日志确认：
1. 计数确实跨天清零、目标重新开始尝试；
2. 被放弃的目标当天确实没有"本可以成功却被放弃"的情况；
3. `config/<uid>/status.json` 的 `failureCountTodayList` 里，
   会员宝箱是否出现多个 `member::treasureBox::*`（若出现 → 见 L5 的反向风险）；
4. 信用2101 的失败是否以空响应为主（若是 → 该 key 永不触发放弃，见 L2 副作用）。

## 4. 判定表（`RepeatFailurePolicy.kindOf`）

**优先匹配确定性**（同一回应同时命中两类时判为确定性）。判据取自**服务端回应本身**的字段/文案：

| 类别 | 判据（子串，大小写不敏感） |
| --- | --- |
| `DETERMINISTIC` 确定性失败 | `param_illegal`、`生活记录模板不存在`、`模板不存在`、`任务还没有完成`、`quota_user_not_enough`、`不可重试`（运动球任务的 `CAMP_TRIGGER_ERROR`）；另有 `不支持rpc完成`（**当前无接入点传入，为同类场景预留**） |
| `TRANSIENT` 服务端不可用 | `系统繁忙`、`繁忙`、`系统出错`、`"error":3000`、`"error": 3000`（两种写法都收）、`请稍后重试`、`限流`、`网络`、`超时`、`timed out` |
| `UNKNOWN` 未判定 | 以上都不命中（**按继续尝试处理**） |

**不计入失败预算**（见 L2）：

| 判据 | 含义 |
| --- | --- |
| `rpc_verification_required`、`触发安全验证`、`请进行验证后继续`、`为保障您的正常访问`、`为了保障您的操作安全` | 触发安全验证（暂停 + TTL 自愈）。前 4 条文案与 `VerificationPausePolicy.VERIFICATION_TEXTS` 同源，由测试交叉断言锁死 |
| `empty_rpc_response` | RPC 返回为空（离线 / 网络抖动 / 占位） |

> 说明：早期版本曾把代码自己写的日志文案（`返回为空或非 SUCCESS`）当判据，
> 但调用方传的是**服务端响应**，该文案实际不可达 —— 已移除，避免"文档有、实际不生效"。

## 6. 新增一个接入点怎么做

1. 确认该目标**一天最多成功一次**（否则见 L6），且失败来自"服务端回应"而非异常（见 L7）；
2. 选稳定 key：`模块::动作`；**带循环/多实例的必须带区分字段**（见 L5）；
3. 调用前 `if (RepeatFailureGuard.shouldSkipToday(KEY)) return`；
   **若"跳过"会导致整段流程静默，请在流程入口判断**，否则失败分支仍会每轮写日志（见 §2）；
4. 失败分支 `RepeatFailureGuard.recordFailure(KEY, "给用户看的名字", 回应文本…)`
   —— 尽量传 `resultCode`/`resultDesc`/整段响应，便于归类；**不要传代码自己写的日志文案**；
5. 在 §5 表里登记这一行（含**真实副作用**），并在 PR 描述里写清"为什么它可以被放弃"。
