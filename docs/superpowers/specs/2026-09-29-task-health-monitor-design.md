# 任务健康状态机设计

## 背景

用户反馈的头号问题是「**明明有好友能量可以收，但就是不动，重启支付宝也没反应，从日志里也看不出怎么了**」。

排查这类问题时，已有的观测手段全部是**事后计数**：

| 已有 | 能回答 | 不能回答 |
| --- | --- | --- |
| `TaskRunCounter` | 今天跑了几次、成败各多少 | 此刻在不在跑 |
| `TaskStatisticsRecorder` | 当日汇总 | 卡在哪一步 |
| `DailyTaskLogRecorder` / `daily_once.json` | 哪些任务做成了 | 没做成的是因为卡住、还是被拦下 |
| `record.log` | 历史上发生过什么 | 「此刻」是什么状态（得人工 grep 时间戳） |

两次真实故障都卡在同一个缺口上：

1. **静默停摆 52 分钟**（2026-09-28 19:08 → 19:59）：网络失败累计触发离线后，
   离线期间**没有任何东西再去探测**，日志里只剩「顺延 60 秒」约 1700 行噪音，看不出「我们其实什么都没做」。
2. **蹲点空转**：等待任务按 60 秒周期重试，日志刷屏但收不到能量，从日志同样看不出「这是在等」还是「这是卡住了」。

结论：缺的是**「此刻健康吗」**这一层，它不是「今天做了几次」的另一种聚合，而是**一个新的维度**。

## 目标

1. 主页能一眼看到主链路任务的当前状态，不需要翻日志。
2. 「不动了」要能被**显式**表达成「卡住 · 已 N 分钟无进展」，这个 N 就是排查的起点。
3. **被暂停**要和**卡住**分开 —— 前者等自愈 / 人工过验证，后者是任务本身出问题，处置方式完全不同。
4. 宿主进程被杀（文件停在 RUNNING）时，界面照样能识别为卡住。
5. **只观测，不干预**：不得自动重试 / 取消 / 重启任务。
6. 阈值可调（默认 5 分钟），判定错了最多显示不准。

## 实现设计

### 核心约定：宿主写事件，读的一方现算状态

任务跑在**支付宝进程**，界面在**模块 App 进程**，内存态跨不过去。若落盘时把结论写死，
宿主进程一被杀，文件就永远停在 `RUNNING`，界面看不出区别。

所以 `task_health.json` 只存**时间戳与计数**，状态由 `TaskHealthPolicy.evaluate` 现算：

```text
宿主进程（任务里）                    界面进程（主页卡片）
  onStart / onProgress                 读 task_health.json
  onSuccess / onFailure           →    按 evaluate() 现算
  onWaiting / onBlocked                「已 N 分钟无进展」
        ↓ 状态变化即写、进展节流 3s
   config/<uid>/task_health.json
```

### 文件与职责

| 文件 | 职责 |
| --- | --- |
| `task/TaskHealthPolicy.kt` | **纯逻辑**：状态枚举、快照 data class、`evaluate` / `labelOf` / `describe`、阈值夹取、自然日键。可单测 |
| `task/TaskHealthMonitor.kt` | 宿主侧事件入口 + 节流落盘 + `readAll`（给界面） |
| `ui/screen/card/TaskHealthCard.kt` | 主页卡片，只展示 |
| `ui/viewmodel/MainViewModel.kt` | `refreshTaskHealth()`，每 5 秒刷新（仅主页） |
| `model/BaseModel.kt` | 新增 `taskStallTimeoutMinutes`（默认 5） |

### 七个状态

`IDLE` 未开始 / `RUNNING` 进行中 / `WAITING` 等待中 / `OK` 正常 / `FAILED` 失败 / `BLOCKED` 已暂停 / `STALLED` 卡住。

**判定优先级：被暂停 > 卡住 > 记录的状态。**

```kotlin
if (blockedReason.isNotEmpty() && state != IDLE) return BLOCKED
if (state != RUNNING && state != WAITING) return state
return if (now - max(lastProgressAt, lastStartAt) > stallTimeoutMs) STALLED else state
```

「卡住」的口径刻意**只看无进展、不看有没有失败**：失败会照常记 `FAILED`，
而卡住的特征恰恰是「既没失败也没进展」—— 这类沉默停摆最难发现。

### 监测范围（只挑主链路）

| ID | 显示名 | 埋点位置 |
| --- | --- | --- |
| `forest.main` | 森林主任务 | `AntForest` 一轮的开始 / 成功 / 失败，外加**每个相位边界**与**按好友收能量**的进展（2026-10-01 追加：只留整轮结束一个点会误报「卡住」） |
| `forest.collect` | 收能量 | `AntForest.collectEnergy` 的开始 / 按好友进展 / 成功 |
| `forest.waiting` | 蹲点收取 | `EnergyWaitingManager` 的等待 / 完成 / 终止 / 重试 |

只做这三项，不做全量：卡片要一眼看完，铺满几十项反而失去意义。
`blockedReason` 是**全局**的（离线拦的是所有 RPC），所以离线时三项都会显示「已暂停」。

### 落盘节流

收能量是**按好友逐个** `onProgress` 的（几十个好友 = 几十次事件）。
规则：状态**变化**立即写并打一行日志；同状态下的进展事件只更新内存，落盘最少间隔 3 秒。
这样既不丢状态迁移，也不会按人写文件、按人刷日志。

### 落盘以磁盘为准：跨进程接续 + 跨天清痕

宿主进程一重启内存就是空的。若直接把内存态写出去，已经跑完的状态会被抹成「未开始」——
而「重启支付宝看看」正是最常用的排查动作，抹掉历史等于自断线索。

所以每次写盘前先 `syncDailyState(now)`：把磁盘上的记录读回来，
按**记录里的最新时间戳**判定归属（`TaskHealthPolicy.belongsToToday`）—— 是今天的接过来继续用，
不是今天的丢弃。同一自然日内只读一次盘（`loadedDay` 短路）。

> 这一条同时取代了「跨天清痕」：`Status.hasFlagToday` 那套 `flagList` 跨天会自己清，
> 这里的文件不会，所以必须以时间戳判定，否则昨天 23:59 的「正常」会挂到今天。

### `blockedReason` 必须跟着落盘

它是**全局**的（离线拦的是所有 RPC），但只活在内存里。若在 `ordered()` 里不给每一项带上再落盘，
界面读文件时根本拿不到它，「已暂停」就永远显示不出来 —— 只会看到「卡住」，把人往完全错误的方向带。

## 错误处理

| 情况 | 处理 |
| --- | --- |
| 文件读不出 / JSON 损坏 | `runCatching` 兜底为空列表，卡片显示「还没有任务状态记录」，不影响主页其它卡片 |
| uid 为空（模块 App 进程） | `resolveHealthFile` 扫 `config/` 下的账号目录，取**最近改过**的那份 |
| 宿主进程被杀，状态停在 RUNNING | 这正是设计要覆盖的场景：按时间戳现算 → 显示「卡住 · 已 N 分钟无进展」 |
| 跨天 | `syncDailyState()` 按记录时间戳判定归属，不是今天的丢弃 |
| 支付宝重启 | 内存态清空前先把磁盘上属于今天的记录接回来，**不会**把已跑完的状态抹成「未开始」 |
| 阈值越界 | `normalizeTimeoutMinutes` 夹到 1–120 |

**不做**的事：任何自动重试、取消、重启。自动处置（类似 `StallActionPolicy`）留给以后，
且必须有用户开关 —— 判定错了的代价必须只是「显示不准」。

## 测试

`app/src/test/java/fansirsqi/xposed/sesame/task/TaskHealthPolicyTest.kt`：

1. 进行中且未超阈值 → `RUNNING`
2. 进行中超阈值 → `STALLED`
3. 等待中**不**算卡住（等能量成熟是正常状态）
4. OK / FAILED 不受阈值影响
5. 被暂停优先于卡住（暂停时不报 STALLED）
6. 未开始的任务即使全局暂停也显示 `IDLE`
7. `describe` 在无进展时输出「已 N 分钟无进展」
8. 阈值夹取：0 → 1，999 → 120
9. 成功时间戳/连续失败次数的文案组装

10. `belongsToToday`：今天的记录算今天、昨天的丢弃、看的是**最新**时间戳、全零按属于今天处理

## 验证过的真实场景（设备）

- 正常态：森林主任务「正常 · 耗时 33秒 · 上次成功 08:44」、收能量「正常 · 收 0g · 上次成功 08:44」、蹲点收取「未开始」
- 异常态（构造 20 分钟前的时间戳）：森林主任务「**卡住** · 已 20 分钟无进展」、收能量「**失败** · 连续失败 2 次」、
  蹲点收取「**已暂停** · 当前网络不可用」，标题右侧「⚠ 3 项需关注」
